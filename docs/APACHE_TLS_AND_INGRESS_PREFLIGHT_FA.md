# Apache TLS-origin و آماده‌سازی مسیر Cloudflare

۲۶ نوامبر ۲۰۲۶. تغییر کد cca567dd82138e2f04a30de3ad4bde3926b3b742 روی سرور نصب شد؛ نسخه قبلی دو ابزار پشتیبان گرفته شد. CI safety و UI موفق. آزمون خصوصی Apache با --tls-origin، TLS certificate validation، HTTP 200 بدون redirect ناخواسته، HTTPS=on و SERVER_PORT=443، Secure/HttpOnly cookie، حذف هدر جعلی و rollback موفق. حالت private HTTP پیش‌فرض تغییر نکرد. فایل‌ها و حساب مصنوعی پاک شدند؛ ۱۸ کانتینر و سرویس‌های اصلی فعال. Feast کاملاً خارج از محدوده و بررسی.

آمادگی ingress: zone Cloudflare فعال؛ hostname پیشنهادی رکورد exact ندارد، اما wildcard A پروکسی‌شده وجود دارد. tunnel اختصاصی با نام پیشنهادی موجود نیست. cloudflared 2026.10.7 محلی syntax unix+tls، originServerName، httpHostHeader، caPool، noTLSVerify=false و catch-all 404 را پذیرفت؛ rule مطابق hostname و rule 404 برای نام دیگر موفق. --token-file پشتیبانی می‌شود. هیچ تونل یا رکورد DNS ایجاد نشده، هیچ secret خوانده یا منتقل نشده؛ آزمون واقعی اتصال Cloudflare و گواهی عمومی انجام نشده است.

فایل infra/ingress/engine-canary.review.yml فقط نمونه بازبینی بدون credentials است. برای انتشار عمومی canary مصنوعی: (1) مجوز مستقل root با محدوده دقیق public ingress (2) حساب connector مستقل بدون login، نه nobody و نه گروه مالک کلید gateway؛ ACL فقط روی traversal مسیر runtime و socket مشخص، lifecycle fail-closed هنگام stop/restart (3) گواهی origin مطابق hostname با trust CA جدا؛ کلید فقط gateway (4) tunnel مستقل، token-file/credential امن و بدون خروجی secret یا argv ثبت‌شونده؛ connector موجود MCP و wildcard دست‌نخورده (5) route exact و 404 پیش‌فرض، noTLSVerify=false؛ پس از سلامت connector و origin، DNS exact مستقل (6) آزمون HTTPS عمومی، mismatch و rollback، بدون اتصال پروژه مشتری. قبل از public، کنترل endpoint، منابع، سیاست دسترسی و سازگاری اپلیکیشن الزامی است. حذف canary فقط رکورد و tunnel متعلق به همان canary و فایل‌های همان پروژه، نه منابع مشترک.
